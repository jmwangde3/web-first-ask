# web-first-ask (wfa) 用户需求规格书

* **定位**：单机使用的 Node.js CLI（原生 CDP 驱动 Chrome，零运行时依赖，不再依赖 `ask-bridge`）+ 极简 Skill。

* **说明**：本文仅定义**目标、能力与边界约束**，不限定具体实现方式；缺陷跟踪与各分支实现细节见仓库 `docs/backlog.md`。

* **更新日期**：2026-11-27

## 一、核心目标与架构定位（原 #1、#2、#3、#5、#11、#15）

1. **脱离 `ask-bridge`**：核心能力完全由 `wfa` 自身完成，不再依赖上游 `ask-bridge`。

2. **重 CLI、轻 Skill**：大部分能力内置在 `wfa` CLI 中；Skill 保持极简，仅负责引导本地 Agent（Codex、Workbuddy 等）正确调用 `wfa`，尽量减少上下文与 token 消耗。

3. **外接大脑分工**：

   * 让本地 Agent 通过 `wfa` 调用 **Gemini（新会话默认 Task 模式）**、**ChatGPT 网页版（沿用网页端持久保存的高思考强度）**、**Claude 网页版** 完成规划、检查、排错与实现；

   * 凡是网页端 provider 能负责的工作全部委派，本地 Agent 仅在 provider 无法获知本地信息或无法直接操作本地环境时代劳；

   * **用户明确指定调用 `wfa` 时，本地 Agent 严禁自行思考或替代回答**（用户另有说明的除外）。

4. **默认开启 Debug 问题记录**：

   * 默认开启问题记录模式（允许手动关闭），使用 `wfa` 遇到失败或异常时自动落盘，并支持本地 Agent 手动补充复现信息；日志需有大小上限，避免长期无限膨胀；

   * Skill 需明确约束本地 Agent：遇到 `wfa` 问题**只记录如何复现，严禁自行修改或修复 `wfa` 自身代码**。

## 二、多模型协作与并发调度（原 #4、#6、#7、#10、#27）

1. **默认多 provider 并行提问**：支持同时向多个 provider 提问以获得更好结果；未指定 provider 时，默认同时向 **ChatGPT 网页版 + Gemini** 提问，各自产出互不干扰。

2. **高并发与锁可靠性**：至少支持 **4 个 Gemini + 4 个 ChatGPT** 同时运行、互不串台且各自稳定拿到结果；Windows 并发场景下的锁与状态写入必须严格排他、内容完整，不得因并发文件竞争偶发报错或损坏状态。

3. **同 provider 新会话错峰**：同一 provider 并发发起新会话时，必须强制随机间隔 **3–5 秒**，模拟真人操作节奏，避免同时触发风控。

4. **代码仓库读取与改代码规则**：

   * **需要修改代码的任务（默认）**：必须直接向 provider 提供代码包，并要求其执行 `git apply --check` 与完整 `npm test` 后再交付；

   * **纯阅读/查证类代码任务**：优先让 provider 自行读取 GitHub 代码；因缓存等原因读不到时，由本地 Agent 打包代码再发给 provider；请求状态不明时不得盲目重发。

5. **交互问答边界**：provider 遇到不了解本地情况的问题时，先由本地 Agent 代答；涉及无法确定的用户决策必须询问用户，得到答复后再继续，不得擅自猜测。

## 三、浏览器控制、反风控与拟人化（原 #13、#14、#19、#21、#23、#24、#25）

1. **原生 CDP 驱动与低特征暴露**：使用 CDP 接口控制真实 Chrome（不用 Playwright 以规避 ChatGPT 风控）；保持贴近普通用户浏览器的最小化启动参数与协议调用，减少自动化暴露面。

2. **双模式与前台无干扰**：支持后台/无干扰模式（不得抢占前台焦点、不得干扰桌面工作或全屏游戏）与前台可见模式（便于调试或人工审阅/接管）。

3. **单 Chrome、单 Profile、多标签复用**：不同 provider 共用同一个 Chrome 窗口与同一套 Profile，不同会话使用独立标签页；避免频繁开关 Chrome，确认拿到结果前不随意关闭，需要人工干预时保留窗口；人工登录与二次验证过程不得被自动跳转打断。

4. **隐私与环境一致性**：

   * 开启 WebRTC 防泄漏，避免暴露真实/局域网 IP；

   * 浏览器时区需保持为 `Asia/Tokyo`（若本机系统时区已是 `Asia/Tokyo`，则无需额外强制覆写）。

5. **拟人化操作与节奏控制**：

   * 日常操作随机间隔 **1–2 秒**，批量操作随机间隔 **4–6 秒**，大批量连续操作需有批间长休眠，严禁 0 间隔批量操作；

   * 关键交互尽量模拟真实用户操作而非明显脚本痕迹（逐字拟人打字与完整鼠标移动曲线列入后续待做）。

6. **中英文界面兼容**：ChatGPT 与 Gemini 的核心功能（收发、停止、读回答、上传附件、模式切换、登录识别、删除会话）需同时支持中文和英文网页界面。

## 四、多形态输入、附件与下载（原 #8、#12、#20）

1. **多形态输入**：支持多样化的提问与上下文输入形式，满足不同使用场景。

2. **全格式附件上传**：支持上传与读取 ChatGPT、Gemini 网页端支持的各类附件（包括但不限于压缩包、图片、文档等，Gemini 支持解压 `.zip`），并在提交前确认附件已真正生效。

3. **代码包下载**：当 provider 回复生成可下载的代码包或附件时，`wfa` 需能自动下载到本地并保证文件完整。

## 五、会话复用与清理（原 #9、#22、#29）

1. **同会话续聊**：同一任务会话尽量交给 provider 里的同一个远端对话以保留上下文、便于管理，避免不断开新对话；接近平台轮次上限（约 40 轮）时再提示或换新。

2. **自动清理**：仅对“一次性新会话”在确认拿到结果后自动清理（允许用户选择保留）；命名/续聊会话默认保留，未完成会话不得自动误删。

3. **手动批量清理**：

   * 提供清理 `wfa` 打开的会话的能力，支持**全清**或**保留未完成**等模式，且**只能清理 `wfa` 创建的会话，绝不得误删用户原有对话**；

   * 批量清理不得每删一条就新开一个标签页，需控制节奏（含批间停顿）并如实区分已确认删除与失败/跳过数量。

## 六、工程与安全边界（原 #16、#17、#18、#26、#28）

1. **单机信任模型**：单机单操作者使用、不涉及远程暴露，不做不合理的安全性拦截或敏感材料发送限制；保持代码简洁、可读性好、零运行时依赖。

2. **实测为准与测试防风控**：开发过程不过分堆砌测试，以真实环境实测为准；验收与测试同样要控制间隔防止触发风控；参考历史 `ask-bridge` 测试结果时不可盲信。

3. **冲突透明**：如需求之间在技术实现上存在冲突，必须先告知用户来取舍，不得私自违背需求自行设计。

## 七、已核实的 Provider 沙箱能力（客观事实参考，2026-11-26）

| Provider / 模式 | 读取 GitHub | 沙箱运行环境 | 代码修改与验证能力 |
| ----- | ----- | ----- | ----- |
| **ChatGPT 网页版** | 可用 GitHub API 读指定 commit 的文件与目录树；**不能 `git clone`**（容器无法解析 `github.com`，强指 IP 也失败） | Git `2.47.3`、Node `22.16.0`、npm `10.9.2` | 传入 `git bundle` 或带 `.git` 的 zip 后，可自建 clone、跑 `git apply --check` / `--stat` 与**完整 `npm test`** |
| **Gemini Chat 模式** | **不能读 GitHub** | 仅 Python `3.10`（无 `node` / `npm` / `git` / `patch`） | 可解压源码 zip、改代码并用 `diff -u` 生成补丁；**跑不了 `npm test`** |
| **Gemini Task 模式** | **Pro 账户可 `git clone` 仓库**；免费版账户不可以 | Node `18.20.4`、npm `9.2.0`（不可联网装依赖） | 可在沙箱内操作源码与运行离线测试（注意 Node 版本为 `18.20.4`，不满足 `>=22.15` 的项目需留意兼容性） |
